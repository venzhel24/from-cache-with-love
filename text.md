## Слайд 3: Что такое кеширование?

**Техническое определение:**
Кеширование — это механизм хранения временных данных в быстром хранилище с целью ускорения доступа к ним. При запросе данных система сначала проверяет кеш. При наличии данных (cache hit) они возвращаются немедленно. При отсутствии (cache miss) данные извлекаются из основного источника, возвращаются пользователю и сохраняются в кеше для последующих запросов. На диаграмме показаны компоненты кеша, включая ключ, значение, TTL и механизм инвалидации.

## Слайд 4: Админ-панель добро.рф

**Техническое описание:**
Пример административной панели портала добро.рф. Сложный интерфейс с высокой нагрузкой на бэкенд из-за большого количества данных, виджетов и фильтров. Без кеширования загрузка страницы требует выполнения множества запросов к базе данных и сложных вычислений, что значительно увеличивает время отклика.

## Слайд 5: Админ-панель с кешем

**Техническое описание:**
Та же административная панель, но с включенным кешированием. Система загружается быстро и работает отзывчиво. Часто используемые данные (списки, отчеты, фильтры) подгружаются из кеша, что минимизирует нагрузку на сервер и сокращает время отклика. Реализация включает в себя кеширование запросов к БД, результатов вычислений и статических ресурсов.

---

## Слайд 6: Админ-панель без кеша

**Техническое описание:**
При отключении или сбое кеширования система становится крайне медленной, перестает отвечать на запросы или вовсе падает. Это демонстрирует критическую важность кеширования для поддержания производительности и стабильности высоконагруженных приложений. Без кеша каждый запрос требует полной обработки на бэкенде, включая запросы к базе данных и выполнение сложных вычислений, что приводит к значительному увеличению времени отклика и нагрузке на серверы.

## Слайд 7: Ключевые термины

**Технические определения:**
- **Hit rate / miss rate:** Процентное соотношение успешных (hit) и неуспешных (miss) обращений к кешу. Высокий hit rate — основной показатель эффективности кеширования.
- **TTL (Time To Live):** Время жизни записи в кеше, после которого она считается устаревшей и подлежит удалению или обновлению.
- **Тёплый / холодный кеш (cache warming):** Холодный кеш — пустое кеш-хранилище, тёплый кеш — содержащий актуальные данные. Прогрев кеша — процесс предварительного заполнения кеша данными до их запроса пользователями.
- **Stale data (Устаревшие данные):** Данные в кеше, которые не соответствуют текущему состоянию основного хранилища.
- **Eviction rate (Коэффициент вытеснения):** Скорость удаления записей из кеша, обычно связанная с нехваткой места и алгоритмами вытеснения (LRU, FIFO и др.).
- **Инвалидация:** Процесс принудительного удаления или пометки записей в кеше как недействительных. Ключевой механизм для предотвращения использования устаревших данных.

## Слайд 8: Цепочка кешей (DNS)

**Техническое описание:**
Путь любого веб-запроса начинается с разрешения доменного имени через DNS. На этом этапе происходит кеширование соответствий доменных имен и IP-адресов. DNS-кеш может находиться на нескольких уровнях: локальный кеш операционной системы, кеш резолвера провайдера, кеш публичных DNS-серверов (например, 8.8.8.8).

---

## Слайд 9: DNS-кеш

**Техническое описание:**
DNS-кеш хранит кешированные записи о соответствиях доменных имен и IP-адресов. При обращении к домену (например, `google.com`) система сначала проверяет локальный DNS-кеш. При отсутствии записи запрос направляется к DNS-резолверу (провайдера или публичному, как `8.8.8`), который также использует кеширование. Это предотвращает выполнение полного цикла DNS-поиска при каждом обращении. Команды очистки кеша: `ipconfig /flushdns` (Windows), `sudo killall -HUP mDNSResponder` (macOS), `sudo systemd-resolve --flush-caches` (Linux).

---

## Слайд 10: Идентификация: DNS-кеш

**Техническое описание:**
Признаки работы DNS-кеша: мгновенное разрешение доменного имени, быстрый ответ от утилит `nslookup` или `dig`, отсутствие новых DNS-запросов в анализаторах трафика (Wireshark/tcpdump). Проверка содержимого кеша: `ipconfig /displaydns` (Windows), `dscacheutil -cachedump -entries Host` (macOS). Время жизни (TTL) DNS-записей задается в самой записи и обычно составляет 300-3600 секунд. После очистки кеша время повторного резолва будет значительно больше, чем при наличии кешированной записи.

---

## Слайд 11: Цепочка кешей (Browser)

**Техническое описание:**
Следующий уровень кеширования — браузерный кеш. После получения IP-адреса браузер отправляет HTTP-запрос на сервер, но перед этим проверяет наличие закешированных ресурсов локально. Браузер кеширует статические ресурсы (CSS, JavaScript, изображения, шрифты) в соответствии с HTTP-заголовками, установленными сервером.

---

## Слайд 12: Браузерный кеш

**Техническое описание:**
Браузер кеширует статические ресурсы: CSS, JavaScript, изображения, шрифты. Управление кешированием осуществляется через HTTP-заголовки:
- Заголовок `Cache-Control` — основной инструмент. Директивы `max-age` указывают время жизни ресурса в кеше браузера, `s-maxage` — для кешей промежуточных серверов. `public` разрешает кеширование любыми кешами, `private` — только пользовательским браузером. `no-cache` требует проверки актуальности ресурса перед использованием кешированной версии.
- Заголовки `ETag` и `Last-Modified` используются для валидации кеша. Браузер отправляет их в условных запросах (If-None-Match, If-Modified-Since), и если ресурс не изменился, сервер возвращает статус `304 Not Modified`, позволяя использовать локальную копию.
Дополнительные механизмы: `localStorage`, `sessionStorage`, `IndexedDB` для клиентского хранения данных и `Service Workers` для реализации сложных стратегий кеширования, включая офлайн-работу приложений (PWA).

## Слайд 13: Очистка браузерного кеша

**Техническое описание:**
Для принудительной загрузки ресурсов без использования кеша применяются следующие методы: "жесткое обновление" страницы (`Ctrl+F5` или `Cmd+Shift+R`) — обходит кеш для текущей страницы; универсальное сочетание `Ctrl+Shift+Delete` для полной очистки кеша и данных браузера через интерфейс настроек. Также можно использовать DevTools → Application → Clear storage или команды в консоли браузера для очистки конкретных хранилищ (localStorage, IndexedDB и др.).

---

## Слайд 14: Идентификация: Браузерный кеш

**Техническое описание:**
В DevTools на вкладке Network можно определить использование кеша по следующим признакам: статус `200 (from disk cache)` или `(from memory cache)` означает использование кешированной копии; статус `304 Not Modified` указывает на успешную валидацию кеша; размер `(disk cache)` или `(memory cache)` в колонке Size; нулевое время загрузки в Network Timeline. Заголовки: Request — `If-None-Match`, `If-Modified-Since`; Response — `Cache-Control`, `ETag`, `Last-Modified`, `Age: 0` при свежем кеше. Проверка: DevTools → Network → Disable cache или жесткое обновление (Ctrl+F5 / Cmd+Shift+R).

Заголовки и статус подтверждают отсутствие сетевого взаимодействия для получения этого ресурса.

## Слайд 16: Цепочка кешей (Local proxy)

**Техническое описание:**
Между браузером и внешним миром может находиться локальный или корпоративный прокси-сервер, который также выполняет функции кеширования. Такой прокси может кешировать HTTP-ответы для всех пользователей в одной сети, уменьшая внешний трафик и ускоряя доступ к часто запрашиваемым ресурсам. Примеры: Squid, Microsoft ISA Server, корпоративные HTTP-прокси. Заголовки: `X-Cache`, `X-Cache-Status`, `Via` могут указывать на наличие промежуточного кеша. Время отклика: TTFB может увеличиться на 10-50ms из-за обработки на прокси. Характеристики: может кешировать как статические, так и динамические ресурсы в зависимости от настроек.

---

## Слайд 17: Цепочка кешей (CDN)

**Техническое описание:**
Следующий уровень — CDN (Content Delivery Network), географически распределенная сеть серверов, кеширующих статический контент (JS, CSS, изображения). Популярные провайдеры: Cloudflare, AWS CloudFront, Яндекс.CDN. CDN снижает время сетевой задержки (RTT), обеспечивает защиту от DDoS-атак и уменьшает нагрузку на исходный сервер. Запросы направляются на ближайший edge-сервер, где контент может быть уже закеширован. Время отклика: TTFB 10-50ms (в зависимости от географической близости к edge-серверу).

---

## Слайд 18: CDN

**Техническое описание:**
CDN кеширует статический контент на edge-серверах, расположенных географически близко к конечным пользователям. Это значительно сокращает время сетевой задержки (RTT). Популярные провайдеры: Cloudflare, AWS CloudFront, Яндекс.CDN. CDN также обеспечивает защиту от DDoS-атак. Методы очистки кеша: через панель управления ("Purge Cache"), через API (например, `curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache"`), или метод "cache-busting" (например, `style.css?v=1.2.3`) для принудительной загрузки новой версии файла. Заголовки: `X-Cache: HIT/MISS/BYPASS`, `CF-Cache-Status: HIT`, `X-Served-By`, `Age: секунды` (возраст кеша на edge-сервере).

---

## Слайд 19: Идентификация: CDN

**Техническое описание:**
CDN добавляют служебные заголовки в HTTP-ответы: `X-Cache: HIT/MISS/BYPASS`, `X-Cache-Status: HIT` (Cloudflare, Fastly), `CF-Cache-Status: HIT` (Cloudflare), `X-Served-By: cache-fra19121-FRA` (указывает географическое расположение edge-сервера), `Age: секунды` (возраст кеша на CDN-сервере). Характеристики HIT: TTFB 10-50ms (в зависимости от proximity к edge-серверу), стабильное время ответа, заголовок `Age` растёт между запросами. Проверка: `curl -I https://site.com/style.css`, запросы из разных регионов (с использованием VPN для проверки географической локализации кеша).

---

## Слайд 20: Цепочка кешей (Reverse-Proxy)

**Техническое описание:**
После прохождения через CDN запрос поступает в серверную инфраструктуру, где может быть обработан reverse proxy. Reverse proxy (например, Nginx, Varnish) располагается перед приложением и кеширует HTTP-ответы, позволяя отвечать на повторяющиеся запросы без передачи их на бэкенд. Это значительно снижает нагрузку на приложение и улучшает время отклика. Время отклика: TTFB 5-20ms (в локальной сети), стабильный ответ для одинаковых запросов, отсутствие логов апстрима в access.log бэкенда при HIT. Заголовки: `X-Proxy-Cache: HIT/MISS/EXPIRED`, `X-Cache-Status: $upstream_cache_status`, `X-Varnish: 123456 789012` (HIT если 2 числа), `X-Cache: HIT`, `Via: 1.1 varnish`.

---

## Слайд 21: Reverse Proxy

**Техническое описание:**
Reverse Proxy (например, Nginx, Varnish) размещается перед приложением и кеширует HTTP-ответы. Это позволяет отвечать на повторяющиеся запросы без передачи их на бэкенд, значительно снижая нагрузку на приложение. Очистка кеша в Varnish может выполняться через HTTP-метод `BAN` (например, `curl -X BAN http://site.com/page`), через `varnishadm ban "req.url ~ /page"`, или через telnet. Время отклика: 5-20ms (в локальной сети), стабильный ответ для одинаковых запросов, отсутствие логов апстрима в access.log бэкенда при HIT. Заголовки: `X-Proxy-Cache: HIT/MISS/EXPIRED`, `X-Cache-Status: $upstream_cache_status`, `X-Varnish: 123456 789012` (HIT если 2 числа), `X-Cache: HIT`, `Via: 1.1 varnish`.

## Слайд 22: Конфигурация Varnish

**Техническое описание:**
Пример конфигурации Varnish на языке VCL (Varnish Configuration Language). В секции `vcl_backend_response` устанавливается TTL ответа, добавляется заголовок `Cache-Control` и удаляются куки, чтобы ответ мог кешироваться для всех пользователей. В секции `vcl_deliver` добавляется заголовок `X-Cache` со значением `HIT` или `MISS` для отладки. Пример конфигурации:
```
sub vcl_backend_response {
    if (beresp.ttl > 0s) {
        set beresp.http.Cache-Control = "public, max-age=" + beresp.ttl;
        unset beresp.http.Set-Cookie;
        return (deliver);
    }
}

sub vcl_deliver {
    if (obj.hits > 0) {
        set resp.http.X-Cache = "HIT";
    } else {
        set resp.http.X-Cache = "MISS";
    }
}
```

Проверка: анализ access-логов приложения — при HIT запрос не попадает на бэкенд, следовательно, в логах не будет записи о нем. Также можно использовать `curl -I` для проверки наличия заголовков кеша в ответе. Время отклика: TTFB 5-20ms (в локальной сети), стабильный ответ для одинаковых запросов, отсутствие логов апстрима в access.log бэкенда при HIT.

## Слайд 25: Bitrix: типы кеша

**Техническое описание:**
Bitrix предоставляет развитую систему кеширования с различными уровнями:
- **Управляемый кеш** (Managed Cache): кеширование данных с ручным управлением TTL и инвалидацией.
- **Тегированный кеш** (Tagged Cache): кеширование данных с возможностью групповой инвалидации по тегам (например, `iblock_id_5`, `category_electronics`).
- **Неуправляемый кеш** (Simple Cache): кеширование внешних данных (например, ответов API) с ручной очисткой.
- **Композитный кеш** (HTML Cache): кеширование целых HTML-страниц с возможностью вставки динамических блоков через `createFrame()`.
- **Кеш компонентов и шаблонов**: встроенное кеширование результатов работы компонентов через параметры `CACHE_TYPE`, `CACHE_TIME`, `CACHE_GROUPS`.
- **ORM кеш** (D7): автоматическое кеширование результатов запросов через метод `setCacheTtl()` с автоматической инвалидацией при изменении данных в таблице.

## Слайд 26: Bitrix: Управляемый/Тегированный кеш

**Техническое описание:**
Пример работы с тегированным кешем в Bitrix. Используется метод `startDataCache` с указанием TTL и уникального ID кеша. Затем регистрируются теги через `startTagCache()` и `registerTag()` (например, `iblock_id_5`, `category_electronics`). При изменении данных, связанных с этими тегами, Bitrix автоматически инвалидирует соответствующие кеш-записи. Ручная инвалидация выполняется через `clearByTag()`. Пример кода:
```php
use Bitrix\Main\Data\Cache;
use Bitrix\Main\Application;

$cache = Cache::createInstance();
$tagCache = Application::getInstance()->getTaggedCache();

if ($cache->startDataCache(3600, 'products_5', '/products/')) {
    $tagCache->startTagCache('/products/');
    $tagCache->registerTag('iblock_id_5');
    $tagCache->registerTag('category_electronics');
    $tagCache->endTagCache();

    $items = getProducts(5);
    $cache->endDataCache($items);
}

// Инвалидация
$tagCache->clearByTag('category_electronics');
```

## Слайд 27: Bitrix: Неуправляемый кеш

**Техническое описание:**
Пример работы с неуправляемым кешем в Bitrix. Используется метод `initCache()` для проверки наличия кеша. При наличии — данные извлекаются через `getVars()`. При отсутствии — запускается кеширование через `startDataCache()`, данные извлекаются из внешнего источника (например, `callExternalAPI()`), сохраняются в кеш через `endDataCache()` и возвращаются. Очистка выполняется вручную через `clean()`. Пример кода:
```php
use Bitrix\Main\Data\Cache;

$cache = Cache::createInstance();
$cacheId = 'external_api_data';
$cacheDir = '/api/external/';

if ($cache->initCache(3600, $cacheId, $cacheDir)) {
    $result = $cache->getVars();
} elseif ($cache->startDataCache()) {
    $result = callExternalAPI();
    $cache->endDataCache($result);
}

// Ручная очистка
$cache->clean($cacheId, $cacheDir);
```

## Слайд 28: Bitrix: Композитный кеш

**Техническое описание:**
Композитный режим — технология гибридного кеширования страниц в Bitrix. ## Слайд 35: Symfony: HTTP кеш

**Техническое описание:**
Symfony позволяет управлять HTTP-кешированием прямо из контроллера. В этом примере создается объект `Response`, затем с помощью методов `setPublic`, `setMaxAge` и `setETag` устанавливаются необходимые HTTP-заголовки. Это инструкция для reverse-прокси и браузеров, как кешировать данный ответ. Пример кода:
```php
use Symfony\Component\HttpFoundation\Response;

public function index(): Response
{
    $response = $this->render('page/index.html.twig');

    // Public cache с max-age
    $response->setPublic();
    $response->setMaxAge(3600);
    $response->setSharedMaxAge(3600);

    // ETag для валидации
    $response->setETag(md5($response->getContent()));

    return $response;
}
```
Заголовки, которые могут быть установлены: `Cache-Control`, `ETag`, `Last-Modified`, `Expires`. Это позволяет эффективно использовать промежуточные кеши (Varnish, CDN) и браузерный кеш. Время отклика для повторных запросов может сократиться до 10-50ms при HIT на прокси или CDN. Заголовки `X-Symfony-Cache: GET /: fresh` могут быть добавлены для отладки. Стратегии кеширования: `public` (для всех кешей), `private` (только для браузера), `no-cache`, `no-store`, `must-revalidate`. Также можно использовать `Vary` заголовки для кеширования разных версий ответа в зависимости от заголовков запроса (например, `Accept-Encoding`, `User-Agent`).

## Слайд 36: Symfony: Cache Pools

**Техническое описание:**
Это основной способ кеширования данных в приложении. Используется сервис, реализующий `CacheInterface`. Метод `get` принимает ключ и callback-функцию. Если данных по ключу в кеше нет, Symfony выполнит callback, сохранит результат в кеш с указанным TTL и вернет его. При последующих вызовах результат будет браться из кеша. Пример использования:
```php
use Symfony\Contracts\Cache\CacheInterface;
use Symfony\Contracts\Cache\ItemInterface;

public function __construct(private CacheInterface $cache) {}

public function getProducts(): array
{
    return $this->cache->get('products_list', function (ItemInterface $item) {
        $item->expiresAfter(3600); // TTL 1 час

        return $this->productRepository->findAll();
    });
}

// Очистка пула
$this->cache->delete('products_list');
```
Cache Pools могут использовать различные адаптеры: Redis, Memcached, файловая система, APCu. Для отладки можно использовать Symfony Profiler, где видны все хиты, миссы и время записи в кеш. Метод `isHit()` у объекта `ItemInterface` позволяет проверить, был ли элемент найден в кеше. Время выполнения callback не вызывается при HIT, что позволяет значительно сократить время отклика приложений. Пулы кеша могут быть настроены в `config/packages/cache.yaml` с различными параметрами: TTL по умолчанию, тегирование, провайдер и др. Также можно использовать `Cache Clearer` для программной очистки пулов. Пулы могут быть настроены с поддержкой тегов для групповой инвалидации. Каждый пул может использовать разные адаптеры и стратегии хранения в зависимости от требований к производительности и персистентности данных.

## Слайд 37: Symfony: Tag-aware Cache

**Техническое описание:**
Tag-aware Cache — мощный инструмент для групповой инвалидации. При сохранении элемента в кеш можно присвоить ему один или несколько тегов. Пример использования:
```php
use Symfony\Contracts\Cache\TagAwareCacheInterface;

public function __construct(
    private TagAwareCacheInterface $cache
) {}

public function getProductsByCategory(int $categoryId): array
{
    return $this->cache->get("products_cat_{$categoryId}",
        function (ItemInterface $item) use ($categoryId) {
            $item->tag(['products', "category_{$categoryId}"]);
            $item->expiresAfter(3600);

            return $this->productRepository->findByCategory($categoryId);
        }
    );
}

// Инвалидация всех продуктов категории
$this->cache->invalidateTags(['category_5']);
```
При изменении данных в категории вызов `invalidateTags()` удаляет все записи, помеченные соответствующими тегами. Это особенно полезно для кеширования связанных данных, когда изменение одного элемента требует очистки множества кеш-записей. Теги могут быть иерархическими (например, `category_5`, `subcategory_5_10`) для более точного управления кешем. Symfony автоматически отслеживает связи между тегами и кеш-записями, что позволяет эффективно управлять сложными сценариями инвалидации. Для отладки можно использовать Symfony Profiler, который показывает теги, связанные с каждым элементом кеша. Также теги можно использовать для очистки групп кеш-записей по признакам, например, все кеши, связанные с определенным пользователем или правами доступа.

## Слайд 38: Symfony: Doctrine кеш

**Техническое описание:**
Doctrine предоставляет несколько уровней кеширования:
- **Result Cache** кеширует результаты конкретных DQL-запросов. Пример использования:
```php
$query = $em->createQuery('SELECT p FROM App\Entity\Product p');
$query->enableResultCache(3600, 'products_all');
$products = $query->getResult();
```
- **Second Level Cache (L2)** — более продвинутый кеш, который хранит данные сущностей. Когда вы запрашиваете сущность по ID, Doctrine сначала ищет ее в L2 кеше, и только потом идет в базу. Это позволяет кешировать данные между разными запросами. Настройка в `config/packages/doctrine.yaml`:
```yaml
doctrine:
  orm:
    second_level_cache:
      enabled: true
      region_cache_driver:
        type: redis
        id: 'doctrine.cache.redis'
```
- **Query Cache** кеширует подготовленные SQL-запросы (планы выполнения)
- **Metadata Cache** кеширует информацию о структуре сущностей
- **Hydration Cache** кеширует результаты преобразования данных в объекты

## Слайд 39: Symfony: Doctrine L2 Cache

**Техническое описание:**
L2 кеш включается на уровне самой сущности с помощью атрибута `#[Cache]`. Пример использования:
```php
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[ORM\Cache(usage: "READ_ONLY", region: "products")]
class Product
{
    #[ORM\Id]
    #[ORM\Column(type: "integer")]
    private int $id;

    #[ORM\Column(type: "string")]
    private string $name;
}

// Очистка L2 Cache
$cacheDriver = $em->getConfiguration()->getResultCacheImpl();
$cacheDriver->deleteAll();
```
Можно указать стратегию (например, `READ_ONLY` для редко изменяемых данных), `READ_WRITE` для данных, которые часто обновляются, или `NONSTRICT_READ_WRITE` для менее строгой консистентности. Регионы позволяют группировать кеш разных сущностей и управлять им. L2 кеш позволяет значительно сократить количество запросов к базе данных при работе с часто используемыми сущностями. Кеширование происходит на уровне Unit of Work, что позволяет избежать повторных запросов в рамках одного HTTP-запроса. Для отладки можно использовать Doctrine Profiler, который показывает статистику использования L2 кеша. Также можно настроить провайдера кеша (Redis, Memcached) для хранения данных L2 кеша в распределенном хранилище.

## Слайд 40: Symfony: Конфигурация пулов

**Техническое описание:**
Гибкость Symfony в том, что разные типы данных можно кешировать по-разному. В файле `config/packages/cache.yaml` можно определить несколько "пулов" кеша. Пример конфигурации:
```yaml
# config/packages/cache.yaml
framework:
    cache:
        app: cache.adapter.redis
        default_redis_provider: 'redis://localhost'

        pools:
            app.cache.products:
                adapter: cache.adapter.redis
                default_lifetime: 360
                tags: true

            app.cache.sessions:
                adapter: cache.adapter.memcached
                provider: 'memcached://localhost'

            app.cache.expensive:
                adapter: cache.adapter.filesystem
                default_lifetime: 86400
```
Каждый пул может использовать разные адаптеры: Redis, Memcached, файловую систему, APCu и др. Пулы могут иметь разные настройки времени жизни по умолчанию, поддерживать тегирование и использовать разных провайдеров. Это позволяет оптимизировать производительность и использование ресурсов под конкретные задачи. Например, для часто используемых данных использовать быстрый Redis, для сессий — Memcached, а для "тяжелых" данных, которые не страшно хранить на диске — файловый кеш. Также можно настроить провайдеров кеша для использования внешних систем хранения. Каждый пул может быть настроен с различными параметрами: сериализация, префиксы ключей, провайдеры, стратегии очистки и т.д.

## Слайд 43: Next.js: виды кеша

**Техническое описание:**
Next.js (с App Router) предлагает многоуровневую систему кеширования:
- **Request Memoization:** Дедупликация `fetch`-запросов в рамках одного рендера. Если одна и та же функция `fetch` вызывается несколько раз в одном рендеринге, на сервере выполняется только один запрос, остальные получают результат из памяти. Работает автоматически для `fetch` и React `cache` функций. Пример:
```js
async function getData() {
   const res = await fetch('https://api.example.com/data')
   return res.json()
}

// В одном рендере:
const data1 = await getData() // запрос отправляется
const data2 = await getData() // берётся из кеша (HIT)
```
- **Data Cache:** Постоянный кеш для результатов `fetch`-запросов на сервере. По умолчанию в Next.js 14 запросы кешируются навсегда (`force-cache`), в Next.js 15 — отключено по умолчанию (`no-store`). TTL задается через `{ next: { revalidate: 60 } }`, тегирование через `{ next: { tags: ['users'] } }`.
- **Full Route Cache:** Кеширование отрендеренного HTML и RSC-пейлоада для статичных страниц. Включается автоматически для статических роутов (без динамических функций). При повторном запросе сервер отдает готовый HTML без рендеринга. Отключается через `'use cache'` или динамические функции (`cookies()`, `headers()`).
- **Router Cache:** Клиентский in-memory кеш, который хранит пейлоад уже посещенных страниц. При навигации по `<Link>` Next.js предзагружает RSC-пейлоад и сохраняет в этот кеш. При переходе страница отображается мгновенно. Очищается через `router.refresh()` на клиенте.

## Слайд 44: Request Memoization

**Техническое описание:**
Механизм предотвращает повторные одинаковые запросы в рамках одного цикла рендеринга на сервере. Если одна и та же функция `fetch` вызывается несколько раз в одном рендеринге, на сервере выполняется только один запрос, остальные получают результат из памяти.
```js
async function getData() {

}

// В одном рендере:
const data1 = await getData() // запрос отправляется
const data2 = await getData() // берётся из кеша (HIT)
```
Это позволяет избежать дублирования запросов к внешним API или базе данных в рамках одного рендеринга компонента. Memoization работает только в пределах одного рендеринга и не сохраняется между разными запросами.

## Слайд 45: Data Cache

**Техническое описание:**
Это основной серверный кеш в Next.js для результатов `fetch`-запросов. В Next.js 14 по умолчанию все `fetch`-запросы кешируются навсегда (`force-cache`), в Next.js 15 — отключено по умолчанию (`no-store`). Для включения кеширования используется `{ cache: 'force-cache' }`. Для отключения — `{ cache: 'no-store' }`. Для задания TTL используется опция `{ next: { revalidate: 60 } }` (ревалидация каждые 60 секунд). Также можно добавлять теги для последующей инвалидации: `{ next: { tags: ['users'] } }`. Примеры:
```js
// Кешировать ответ (по умолчанию в Next.js 14)
fetch('https://...', { cache: 'force-cache' })

// Не кешировать (по умолчанию в Next.js 15)
fetch('https://...', { cache: 'no-store' })

// Кешировать с ревалидацией каждые 60 секунд
fetch('https://...', { next: { revalidate: 60 } })

// С тегами для групповой инвалидации
fetch('https://...', { next: { tags: ['users'] } })
```
Кеш хранится в памяти сервера или в файловой системе, в зависимости от конфигурации.


---
## Слайд 46: Next.js Cache Invalidation

**Техническое описание:**
Инвалидация кеша — ключ к отображению актуальных данных. Функции `revalidateTag` и `revalidatePath` позволяют инвалидировать Data Cache и Full Route Cache. Обычно их вызывают в Server Actions или API-роутах после изменения данных. Пример использования:
```js
import { revalidateTag, revalidatePath } from 'next/cache'

revalidateTag('users')
revalidatePath('/dashboard')

// API Route пример
export async function POST() {
    await updateUser()
    revalidateTag('users')
    return Response.json({ success: true })
}
```
При вызове `revalidateTag` происходит сброс кеша для всех `fetch`-запросов с соответствующим тегом. `revalidatePath` сбрасывает кеш для конкретного пути, включая Full Route Cache. Также можно использовать `revalidatePath('/dashboard', 'layout')` для инвалидации только layout.

## Слайд 47: Full Route Cache

**Техническое описание:**
Full Route Cache — кеширование отрендеренного HTML и RSC-пейлоада для статичных страниц. Включается автоматически для статических роутов (без динамических функций). При повторном запросе сервер отдает готовый HTML без рендеринга. Отключается через `'use cache'` или динамические функции (`cookies()`, `headers()`). Пример:
```js
// layout.tsx или page.tsx
'use cache'

export default async function Page() {
  const users = await fetch('/api/users').then(r => r.json())
  return <div>{users.map(u => <p key={u.id}>{u.name}</p>)}</div>
}
```
Кеш хранится в памяти сервера или в файловой системе. При инвалидации через `revalidatePath` происходит пересоздание кеша при следующем запросе.

## Слайд 48: Router Cache

**Техническое описание:**
Router Cache — клиентский in-memory кеш в Next.js. Когда вы переходите по ссылкам (`<Link>`), Next.js предзагружает RSC-пейлоад следующей страницы и сохраняет его в этом кеше. При навигации страница отображается мгновенно, без запроса к серверу. `router.refresh()` позволяет принудительно очистить этот кеш и запросить свежие данные сервера. Пример:
```js
'use client'
import { useRouter } from 'next/navigation'

export function RefreshButton() {
    const router = useRouter()
    return <button onClick={() => router.refresh()}>Обновить</button>
}
```
Кеш хранится в памяти браузера до перезагрузки страницы или перехода за пределы приложения.

## Слайд 49: Redis Cache

**Техническое описание:**
Redis — это популярное решение для кеширования, используемое в Symfony, Bitrix и других системах. Команды для управления кешем через `redis-cli`: `FLUSHALL` для полной очистки всех баз, `FLUSHDB` для очистки текущей базы данных, пример удаления ключей по маске: `redis-cli --scan --pattern "user:*" | xargs redis-cli DEL`. Также можно использовать `DEL tag:users tag:products` для очистки по тегам. Для мониторинга в реальном времени используется команда `MONITOR`.

Каждый из этих уровней вносит свой вклад в общую производительность системы, снижая время отклика и уменьшая нагрузку на серверы. ## Слайд 52: Многоуровневая диагностика

**Техническое описание:**
Когда что-то идет не так, или вы хотите понять, на каком уровне сработал кеш, нужно действовать методично, исключая уровни один за другим:
1. **Браузер:** DevTools → Network → `(from disk cache)`? → Браузерный кеш. Используйте жесткое обновление (`Ctrl+F5` / `Cmd+Shift+R`) для обхода браузерного кеша.
2.  **CDN:** Заголовки `X-Cache-Status: HIT`? → CDN кеш. Проверка: `curl -I https://site.com/resource`.
3.  **Proxy:** Заголовки `X-Proxy-Cache: HIT`? → Nginx/Varnish. Проверка: анализ access-логов приложения — при HIT запрос не попадает на бэкенд.
4.  **Приложение:** Низкий DB query count? → Прикладной кеш (Redis, Memcached). Проверка: Symfony Profiler, Redis Monitor (`MONITOR`), проверка ключей в кеше.
5. **Redis:** `MONITOR` показывает GET без SET? → Redis HIT. Используйте `redis-cli --scan --pattern "pattern"` для проверки ключей вручную.

## Слайд 53: Стратегии кеширования

**Техническое описание:**
Существует несколько классических стратегий (или паттернов) кеширования. Давайте рассмотрим основные.



---
## Слайд 53: Cache-aside (Lazy Loading)

**Техническое описание:**
Приложение само управляет кешем: сначала проверяет кеш, при промахе — читает из БД, затем сохраняет в кеш. Пример реализации:
```php
// Псевдокод
function getData($key) {
    $data = cache_get($key);
    if ($data === false) {
        $data = db_query($key);
        cache_set($key, $data, TTL);
    }
    return $data;
}
```
**Плюсы:** простота реализации, гибкость в управлении кешем, возможность кеширования только часто используемых данных.
**Минусы:** дублирование логики (проверка кеша) в коде, "холодный" старт (первый запрос всегда медленный), возможна несогласованность данных при конкурентном доступе.



---
## Слайд 55: Read-through

**Техническое описание:**
При этой стратегии приложение обращается только к кешу, как будто это основное хранилище. А уже сам кеш (точнее, провайдер кеша) умеет при промахе загружать данные из БД. Пример реализации:
```php
// Псевдокод
function getData($key) {
    // cache_get сам при промахе вызывает loader для загрузки данных из БД
    return cache_get($key, function() use ($key) {
        return db_query($key);
    });
}
```
**Плюсы:** более чистый код приложения (не нужно вручную проверять кеш), автоматическая загрузка данных при промахе, данные всегда доступны из кеша.
**Минусы:** требует более "умного" провайдера кеша (поддержка read-through), сложнее настройка TTL и управления инвалидацией, может привести к проблемам при высокой нагрузке на БД при промахах.



---
## Слайд 56: Write-through

**Техническое описание:**
При этой стратегии приложение записывает данные одновременно и в кеш, и в БД. Операция считается завершенной только после успеха в обоих хранилищах. Пример реализации:
```php
// Псевдокод
function updateData($key, $value) {
    $db_success = db_update($key, $value);
    $cache_success = cache_set($key, $value, TTL);
    return $db_success && $cache_success;
}
```
**Плюсы:** высокая консистентность данных (кеш всегда актуален), простота реализации логики обновления.
**Минусы:** увеличивается задержка при записи (нужно обновить оба хранилища), возможны проблемы при сбоях в одном из хранилищ.



---

## Слайд 56: Write-behind (Write-back)

**Техническое описание:**
Приложение записывает данные только в кеш и сразу получает подтверждение. А кеш в фоновом режиме, асинхронно, записывает эти данные в БД. Пример реализации:
```php
// Псевдокод
function updateData($key, $value) {
    cache_set($key, $value, TTL);  // Возвращается сразу
    // Асинхронная запись в БД происходит позже
    queue_for_db_write($key, $value);
    return true;
}
```
**Плюсы:** очень быстрая запись для приложения (не нужно ждать записи в БД), снижение нагрузки на БД при большом количестве операций записи, возможность батчевой обработки обновлений.
**Минусы:** риск потери данных, если кеш "упадет" до того, как данные будут сохранены в БД, сложность обеспечения согласованности данных, необходимость обработки ситуаций при сбоях, возможна потеря консистентности при конкурентных обновлениях.


---
## Слайд 58: Refresh-ahead

**Техническое описание:**
Кеш может автоматически обновлять популярные, но скоро истекающие записи, делая это в фоновом режиме до того, как они реально понадобятся. Пример реализации:
```php
// Псевдокод
function getData($key) {
    $data = cache_get($key);
    if ($data !== false) {
        // Проверяем, если TTL меньше 10% от начального значения
        if (cache_ttl_left($key) < cache_initial_ttl($key) * 0.1) {
            // Асинхронно обновляем кеш
            queue_refresh_ahead($key);
        }
        return $data;
    }
    // При промахе загружаем данные
    $data = db_query($key);
    cache_set($key, $data, TTL);
    return $data;
}
```
**Плюсы:** уменьшает задержки для пользователя (данные всегда "свежие"), снижает вероятность промахов кеша, улучшает общую отзывчивость системы.
**Минусы:** может создавать лишнюю нагрузку, обновляя данные, которые больше не нужны, требует хорошего прогнозирования популярности ключей, сложнее реализация логики обновления, возможна конкуренция при одновременных обновлениях.

## Слайд 59: Типовые ошибки

**Техническое описание:**
Несколько типичных проблем, связанных с кешированием:
- **Cache stampede (эффект толпы):** Когда очень популярный кешированный элемент истекает, и тысячи запросов одновременно пытаются его сгенерировать заново, обрушивая бэкенд. Решается с помощью блокировок или стратегии `stale-while-revalidate`. Пример реализации:
```php
// Псевдокод
function getData($key) {
    $data = cache_get($key);
    if ($data === false) {
        // Только один процесс может обновить кеш
        if (acquire_lock("lock:$key")) {
            $data = db_query($key);
            cache_set($key, $data, TTL);
            release_lock("lock:$key");
        } else {
            // Остальные ждут завершения обновления
            wait_for_lock("lock:$key");
            $data = cache_get($key); // Берут обновленные данные
        }
    }
    return $data;
}
```
- **Hot keys (горячие ключи):** Один очень популярный ключ (например, главная страница) может создавать непропорционально высокую нагрузку на один узел кеша. Решается с помощью шардинга, репликации или разделения ключа на несколько подключей.
- **Thundering herd (стадо бизонов):** Похоже на `stampede`, но в более широком смысле — пробуждение множества процессов, ожидающих одного события. Возникает, когда большой объем данных истекает одновременно. Решается с помощью случайной задержки при обновлении или стратегии `stale-while-revalidate`.
- **Memory leak (утечка памяти):** Если забывать устанавливать TTL или неправильно настроить инвалидацию, кеш может бесконтрольно расти, пока не исчерпает всю память. Решается с помощью мониторинга, установки лимитов памяти и автоматической очистки по LRU/FIFO.
- **Stale data (устаревшие данные):** Самая частая проблема — пользователи видят старую информацию из-за некорректной инвалидации кеша. Решается с помощью тегированной инвалидации, мониторинга и тестирования сценариев обновления данных.
