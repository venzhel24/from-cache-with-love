Браузерный кеш

  • Кеширование ресурсов по HTTP:
    • Cache-Control: директивы для управления кешированием (max-age, no-cache, public, private).
    • ETag / Last-Modified - If-None-Match / If-Modified-Since: валидация кеша для избежания повторной загрузки.
  • Хранилища на стороне клиента (localStorage, sessionStorage, IndexedDB)

Браузерный кеш

Признаки работы:
• Статус 200 (from disk cache) или (from memory cache)
• Статус 304 Not Modified при ревалидации
• Size: (disk cache) или (memory cache) и Нулевое время загрузки в Network Timeline

Заголовки:
• Request: If-None-Match, If-Modified-Since
• Response: Cache-Control, ETag, Last-Modified
• Age: 0 при свежем кеше

Очистка:
• DevTools → Network → Disable cache (выключить)
• Hard refresh: Ctrl+F5 / Cmd+Shift+R
• Chrome: Меню → Дополнительные инструменты → Удаление данных

CDN

  • Кеширование статики (JS, CSS, images)

• В панели управления: "Purge Cache"
• API: curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache"
• Cache-busting: style.css?v=1.2.3

CDN

Служебные заголовки:
• X-Cache: HIT / MISS
• X-Cache-Status: HIT (Cloudflare, Fastly)
• CF-Cache-Status: HIT (Cloudflare)
• X-Served-By: cache-fra19121-FRA
• Age: 1234 — возраст кеша в секундах

Характеристики HIT:
• TTFB: 10-50ms (edge proximity)
• Стабильное время ответа
• Заголовок Age растёт между запросами

Проверка:
• curl -I https://site.com/style.css
• Запросы из разных регионов (VPN)

• HTML комментарий: <!-- COMPOSITE_CACHE -->
• Cookie: BX_COMPOSITE_CACHE
• Заголовок: X-Bitrix-Composite: Cache (200)

Компонентный кеш:
• Проверка директорий /bitrix/cache/
• Файлы с префиксом и хешем параметров

Проверка в коде:
• Дебаг: $cache->initCache() возвращает true
• Время выполнения падает в 10-100 раз
• Счётчик запросов к БД не растёт

Next.js: Порядок проверки кешей

При запросе страницы Next.js проверяет кэши в порядке:

  1. Router Cache (клиент) → если HIT, страница из памяти
  2. Full Route Cache (сервер) → если HIT, HTML из билда
  3. Data Cache (сервер) → если HIT, данные из кэша fetch
  4. Request Memoization → дедупликация fetch в рендере
  5. Источник данных / Backend (БД/API) → если все MISS

Каждый уровень ускоряет последующие запросы.

Цепочка кешей

Многоуровневая диагностика

Сценарий: определить, где HIT

1. Браузер: DevTools → (from disk cache)? → Браузерный кеш
2. CDN: X-Cache-Status: HIT? → CDN кеш
3. Proxy: X-Proxy-Cache: HIT? → Nginx/Varnish
4. Приложение: Низкий DB query count? → App cache
5. Redis: MONITOR показывает GET без SET? → Redis HIT

Последовательность исключения:
• Ctrl+F5 → обход браузера
• Cache-Control: no-cache → обход CDN/proxy
• Purge Redis ключ → проверка app layer
• Мониторинг логов на каждом уровне

Типичное время отклика по уровням

Уровень кеша Типичное время отклика (TTFB)
Браузер (memory/disk cache) 0 мс
CDN (edge) 10-50 мс
Reverse Proxy (Varnish, Nginx) 5-20 мс
In-memory (Redis, Memcached) 1-5 мс
Бэкенд (без кеша) 100-1000+ мс

* Время указано для обработки на каждом уровне в изоляции.
Полное время запроса = время обработки + сетевые задержки (RTT) между всеми пройденными уровнями.
Например: пользователь → CDN edge (10-50 мс) + RTT до edge (20-150 мс в зависимости от региона).

Стратегии кеширования

Cache-aside (Lazy Loading)

  • Приложение проверяет кеш
  • При промахе — читает из источника
  • Сохраняет в кеш

Read-through

  • Приложение запрашивает данные
  • Кеш сам читает из источника при промахе
  • Кеш кэширует ответ

Write-through

  • Запись одновременно в кеш и источник
  • Гарантия согласованности
  • Высокая нагрузка на запись

Write-behind (Write-back)

  • Запись только в кеш
  • Асинхронная запись в источник
  • Риск потери данных

Refresh-ahead (Prefetch)

  • Обновление кеша до истечения TTL
  • Снижение latency
  • Требует прогнозирования
