Nginx: Proxy Cache

        # Настройка зоны кеширования
        proxy_cache_path /data/nginx/cache
            levels=1:2
            keys_zone=my_cache:100m
            max_size=10g
            inactive=60m;

        location / {
            proxy_pass http://backend;
            proxy_cache my_cache;
            proxy_cache_valid 200 302 10m;
            proxy_cache_valid 404 1m;
            add_header X-Proxy-Cache $upstream_cache_status;
        }

Bitrix: Управляемый/Тегированный кеш


                    use Bitrix\Main\Data\Cache;
                    use Bitrix\Main\Application;

                    $cache = Cache::createInstance();
                    $tagCache = Application::getInstance()->getTaggedCache();

                    if ($cache->startDataCache(3600, 'products_5', '/products/')) {
                        $tagCache->startTagCache('/products/');
                        $tagCache->registerTag('iblock_id_5');
                        $tagCache->registerTag('category_electronics');
                        $tagCache->endTagCache();

                        $items = getProducts(5);
                        $cache->endDataCache($items);
                    }

                    // Инвалидация
                    $tagCache->clearByTag('category_electronics');

Bitrix: Неуправляемый кеш


                use Bitrix\Main\Data\Cache;

                if ($cache->initCache(3600, $cacheId, $cacheDir)) {
                    $result = $cache->getVars();

Symfony: HTTP кеш


                use Symfony\Component\HttpFoundation\Response;

                public function index(): Response
                {
                    $response = $this->render('page/index.html.twig');

                    // Public cache с max-age
                    $response->setPublic();
                    $response->setMaxAge(3600);
                    $response->setSharedMaxAge(3600);

                    // ETag для валидации
                    $response->setETag(md5($response->getContent()));

                    return $response;
                }

Symfony: Cache Pools


                use Symfony\Contracts\Cache\CacheInterface;
                use Symfony\Contracts\Cache\ItemInterface;

                public function __construct(private CacheInterface $cache) {}

                public function getProducts(): array
                {
                    return $this->cache->get('products_list', function (ItemInterface $item) {
                        $item->expiresAfter(3600); // TTL 1 час

                        return $this->productRepository->findAll();
                    });
                }

                // Очистка пула
                $this->cache->delete('products_list');

Symfony: Tag-aware Cache


                use Symfony\Contracts\Cache\TagAwareCacheInterface;

                public function __construct(
                    private TagAwareCacheInterface $cache
                ) {}

                public function getProductsByCategory(int $categoryId): array
                {
                    return $this->cache->get("products_cat_{$categoryId}",
                        function (ItemInterface $item) use ($categoryId) {
                            $item->tag(['products', "category_{$categoryId}"]);
                            $item->expiresAfter(3600);

                            return $this->productRepository->findByCategory($categoryId);
                        }
                    );
                }

                // Инвалидация всех продуктов категории
                $this->cache->invalidateTags(['category_5']);

Цепочка кешей

Идентификация работы кеша

Диагностика: общий подход

  • Заголовки HTTP — основной источник информации
  • Метрики времени — TTFB, загрузка
  • Служебные маркеры — X-Cache, Age, Via
  • DevTools Network — статусы и таймлайн
  • Логи сервера — hit/miss в реальном времени

Идентификация: DNS кеш

Признаки работы:
• Моментальное разрешение доменного имени
• Отсутствие DNS-запросов в Wireshark/tcpdump
• nslookup возвращает результат мгновенно

Проверка:
• ipconfig /displaydns (Windows)
• dscacheutil -cachedump -entries Host (macOS)
• Очистить кеш и замерить время повторного резолва

Характеристики:
• TTFB: не влияет после резолва
• TTL: задается в DNS-записи (обычно 300-3600 сек)

Идентификация: браузерный кеш

Признаки работы:
• Статус 200 (from disk cache) или (from memory cache)
• Статус 304 Not Modified при ревалидации
• Size: (disk cache) или (memory cache)
• Нулевое время загрузки в Network Timeline

Заголовки:
• Request: If-None-Match, If-Modified-Since
• Response: Cache-Control, ETag, Last-Modified
• Age: 0 при свежем кеше

Проверка:
• DevTools → Network → Disable cache (выключить)
• Hard refresh: Ctrl+F5 / Cmd+Shift+R

Идентификация: браузерный кеш

Идентификация: CDN кеш

Служебные заголовки:
• X-Cache: HIT / MISS / BYPASS
• X-Cache-Status: HIT (Cloudflare, Fastly)
• CF-Cache-Status: HIT (Cloudflare)
• X-Served-By: cache-fra19121-FRA
• Age: 1234 — возраст кеша в секундах

Характеристики HIT:
• TTFB: 10-50ms (edge proximity)
• Стабильное время ответа
• Заголовок Age растёт между запросами

Проверка:
• curl -I https://site.com/style.css
• Запросы из разных регионов (VPN)

Идентификация: Reverse Proxy

Nginx заголовки:
• X-Proxy-Cache: HIT / MISS / EXPIRED
• X-Cache-Status: $upstream_cache_status
• Age: секунды

Varnish:
• X-Varnish: 123456 789012 (HIT если 2 числа)
• X-Cache: HIT
• Via: 1.1 varnish

Характеристики:
• TTFB: 5-20ms (локальная сеть)
• Стабильный ответ для одинаковых запросов
• Отсутствие логов апстрима в access.log бэкенда

Nginx: добавление маркеров

location / {
    proxy_pass http://backend;
    proxy_cache my_cache;
    proxy_cache_valid 200 10m;

    # Добавляем заголовок статуса кеша
    add_header X-Proxy-Cache $upstream_cache_status always;
    add_header X-Cache-Key $scheme$proxy_host$request_uri;

    # HIT, MISS, EXPIRED, STALE, UPDATING, REVALIDATED, BYPASS
}

# В логах
log_format cache_log '$remote_addr - $upstream_cache_status [$time_local] '
                     '"$request" $status';

HTTP кеш:

• Age: секунды — возраст кеша
• X-Content-Digest: хеш

Прикладной кеш:
• Symfony Profiler → Cache панель
• Метрики: hits, misses, write time
• Redis Monitor: MONITOR в реальном времени
• Логи: logger с каналом 'cache'

Идентификация: Redis/Memcached

Redis:
• redis-cli MONITOR — все команды в реальном времени
• redis-cli INFO stats → keyspace_hits/misses
• redis-cli --stat — метрики каждую секунду
• GET key проверка конкретного ключа

Memcached:
• echo "stats" | nc localhost 11211
• get_hits / get_misses — счётчики
• curr_items — количество ключей
• evictions — вытеснения из-за нехватки памяти

Hit rate: hits / (hits + misses) × 100%
Здоровый hit rate: >80% для стабильной нагрузки

  • Browser DevTools — Network, Headers, Timing
  • curl — curl -I -H "Cache-Control: no-cache" URL
  • RedBot — https://redbot.org (анализ кеша)
  • Varnishlog — детальные логи Varnish
  • Redis CLI — MONITOR, INFO, --stat
  • Symfony Profiler — Cache панель
  • Bitrix Debug — LOG_CACHE, панель управления
  • Wireshark/tcpdump — сетевой анализ

Паттерны идентификации: HIT

Явные признаки HIT:
• Заголовки: X-Cache: HIT, X-Proxy-Cache: HIT
• Статус: 200 (from cache), 304 Not Modified
• Age > 0 и растёт между запросами
• TTFB: стабильно низкий (< 50ms для edge)
• Size: (disk cache) или (memory cache)
• Отсутствие в логах апстрима/бэкенда

Проверка:
1. Первый запрос → записываем Age и заголовки
2. Второй запрос → Age увеличился = HIT
3. ETag/Last-Modified не изменились
4. Время отклика стабильно и мало

Паттерны идентификации: MISS

Явные признаки MISS:
• Заголовки: X-Cache: MISS, X-Proxy-Cache: MISS
• Age: 0 или отсутствует
• TTFB: высокий (время генерации на бэкенде)
• Запрос есть в логах апстрима
• Статус: 200 OK (не from cache)

Причины MISS:
• Холодный кеш (первый запрос)
• TTL истёк (EXPIRED → MISS + обновление)
• Cache-Control: no-cache в запросе
• Vary не совпал (Accept-Encoding, Cookie)
• Ручная инвалидация/purge

Многоуровневая диагностика

Сценарий: определить, где HIT

1. Браузер: DevTools → (from disk cache)? → Браузерный кеш
2. CDN: X-Cache-Status: HIT? → CDN кеш
3. Proxy: X-Proxy-Cache: HIT? → Nginx/Varnish
4. Приложение: Низкий DB query count? → App cache
5. Redis: MONITOR показывает GET без SET? → Redis HIT

Последовательность исключения:
• Ctrl+F5 → обход браузера
• Cache-Control: no-cache → обход CDN/proxy
• Purge Redis ключ → проверка app layer
• Мониторинг логов на каждом уровне

Стратегии кеширования

Cache-aside (Lazy Loading)

  • Приложение проверяет кеш
  • При промахе — читает из источника
  • Сохраняет в кеш

Read-through

  • Приложение запрашивает данные
  • Кеш сам читает из источника при промахе
  • Кеш кэширует ответ

Write-through

  • Запись одновременно в кеш и источник
  • Гарантия согласованности
  • Высокая нагрузка на запись

Write-behind (Write-back)

  • Запись только в кеш
  • Асинхронная запись в источник
  • Риск потери данных

Refresh-ahead (Prefetch)

  • Обновление кеша до истечения TTL
  • Снижение latency
  • Требует прогнозирования

Cache warming

  • Предзаполнение кеша при старте
  • Для критичных данных
  • Снижает нагрузку на холодный старт

Типовые ошибки

  • Cache stampede
  • Hot keys
  • Thundering herd
  • Memory leak
  • Stale data
